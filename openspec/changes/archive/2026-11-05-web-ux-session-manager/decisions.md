# web-ux-session-manager 收敛留痕（decisions.md）

> 阶段 1.5 产物；grill-me 三轮前沿提问，用户逐项拍板。本文与 `explore.md`（阶段 1 探索草案）共同构成落档输入；两者冲突处以本文为准。

## 设计树与轮次

```
入口形态 ── Q1（仅全局入口+工作区选择框）
对象范围 ── Q2（三 tab：活跃/已归档/已迁移）──┬─ R1（恢复语义）
                                            ├─ R2（running 处理）
                                            └─ R3（无主条目）
失败语义 ── Q3（预览软失败+执行整单拒绝）──→ T1（批量归档例外：逐项报告）
契约形态 ── Q4（新增批量端点）
变更规模 ── R4（单变更）    变更名 ── T2（web-ux-session-manager）
```

## 第一轮（入口/范围/失败/契约）

| # | 问题 | 用户裁定 | 备注 |
| --- | --- | --- | --- |
| Q1 | 入口落点（视图选项与工作区菜单无上游注入口） | **仅全局入口**（`sidebar.footer.action`）；管理界面提供**工作区选择框**，选定工作区后管理该工作区的会话；**不做**「所有会话」总管理 | 推翻探索草案的"丙：双入口"与"浮层内按工作区分组即可等效全部管理"——用户明确要选择框交互 |
| Q2 | 管理对象范围 | **三 tab 分栏**：①活跃会话→「归档」操作；②已归档会话→「删除」（物理删除/迁移归档二选一）；③已迁移（`$DSH_HOME/archive/sessions` 下）→「删除」（物理）+「恢复」。三种均须支持**全选/部分选择**批量执行 | 推翻草案"A：仅已归档可处置"；范围扩为四能力域 |
| Q3 | 批量失败语义 | **预览软失败 + 执行整单拒绝**（按推荐） | 预览返回可处置集合合并统计 + 被拒清单（id+稳定码），界面剔除并明示；执行重校验，任一失败零副作用整单拒绝；文件动作失败不中止不回滚逐条 warnings |
| Q4 | 契约形态 | **新增批量端点**（按推荐 A） | 现有单会话两端点与契约一字不动，向后兼容 |

## 第二轮（恢复/running/无主条目/规模）

| # | 问题 | 用户裁定 |
| --- | --- | --- |
| R1 | 恢复语义 | **回到已归档状态**（按推荐 A）：目录搬回 `sessions/` 原位 → `projectKey` 正推 attach 到 path 匹配的工作区（匹配不到→未分组）→ 放回归档集合；单步确认；目标位冲突该项失败零副作用 |
| R2 | 批量归档遇 running | **剔除不自动停**（按推荐 A）：预览时 running 项进被拒清单（提示先停止），不自动 `stopActivity` |
| R3 | 无主条目（projectKey 匹配不到任何工作区） | **伪选项聚合管理**（按推荐 A）：工作区选择框加「未匹配工作区的归档」伪选项，聚合无主条目，同样提供删除/恢复 |
| R4 | 变更规模 | **单变更落档**（按推荐 A）：一套 proposal/spec/design/tasks，任务分组批次推进 |

## 第三轮（归档承载/变更名）

| # | 问题 | 用户裁定 |
| --- | --- | --- |
| T1 | 批量归档承载与失败语义 | **客户端循环上游 `archiveSession`，逐项报告结果**（按推荐 A）：归档可逆且上游已有原子单调用，宿主零增量；Q3 整单拒绝仅约束**有文件动作**的删除与恢复——批量归档是 Q3 的显式例外 |
| T2 | 变更名 | **`web-ux-session-manager`**（按推荐 A） |

## 收敛期间查证的事实（不问用户，自证）

| 事实 | 结论 | 用途 |
| --- | --- | --- |
| 视图选项菜单 / 工作区 "..." 菜单 | 上游 0.2.1-rc.5 无注入口（items 硬编码；视图选项仅宽侧栏渲染） | Q1 换道 `sidebar.footer.action` 的依据 |
| `sidebar.footer.action` | list slot，Settings 旁，声明方 dsh-client-ui-sidebar | 全局入口落点 |
| `projectKey(cwd)` 转义 | `/\:` 折叠为 `-`（连续去重）+ `~XXXX` 转义 + 首尾 `--`，**有意有损**：反推不可能、正推完全确定 | R1 恢复 attach、R3 归属过滤按工作区 path 正推目录名比对 |
| jsonl 持久化 `list()` | 每次调用即时扫描磁盘（无缓存） | 恢复搬回目录后宿主列表自然可见 |
| 已迁移会话元数据 | 目录内仅 `session.v4.jsonl.zstd` + 空 `session.lock`；SessionHeader 无 title、日志 zstd 压缩——**标题不可得** | 已迁移 tab 按 sessionId + 体积 + mtime + 项目目录名展示；本机归档根实测存在 `session-<uuid>` 前缀旧目录，枚举按"归档根下两层目录"宽容处理 |
| 上游归档调用面 | `ctx.workspaces.archiveSession(sessionId, { stopActivity })` | T1 客户端循环承载；R2 不用 stopActivity |
| 客户端数据面 | `sessions.list`（ids/byId：displayTitle、origin、updatedAt、running）+ `workspaces.list`（items[].sessionIds/path、全局 archived/pinned 集合） | 浮层三 tab 数据源，只读足够 |

## 遗留到设计期（阶段 1.7）的事项（非待决，实现细节）

- 恢复完成后客户端列表即时刷新的上游事件面查证；无事件则降级为"手动刷新后可见"并在文档记录。
- 浮层交互细节（tab 结构、复选粒度、全选位置、预览摘要形态）；`dsh.client.inject` 增补清单。
- spec 组织：`dsh-web-ux-session-delete` 增量 Requirement vs 新 capability spec，落档（openspec-propose）时定。

### 增补需求的承载裁定（主会话按既有决策推导，非新拍板）

- 「批量取消归档」走 T1 同款例外：客户端循环上游 `ctx.workspaces.unarchiveSession(sessionId)`，逐项报告结果（归档集合操作可逆、无文件动作，不适用 Q3 整单拒绝）；宿主端点零增量。
- tab 2 操作区并存两个动作：「删除」（预览 + 模式 + 确认，Q3 语义）与「取消归档」（可逆操作，轻确认 + 逐项结果）；两动作共享同一选择集合，删除在途时禁用全部交互。
